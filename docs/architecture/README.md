# 아키텍처와 매칭 흐름

[메인 README](../../README.md)

## 이력서 분석

1. 프런트엔드가 PDF 파일을 FastAPI에 업로드합니다.
2. pdfplumber로 텍스트를 추출하고, 예외 상황에는 PyPDF2 경로를 사용합니다.
3. extractor 서비스가 ResumeData 스키마에 맞춰 경력·기술·프로젝트·학력 정보를 추출합니다.
4. OpenAI 또는 인식된 Google 키로 구조화 추출을 시도하고, 실패 시 정규식 기반 파서로 폴백합니다.

## 직무 매칭과 추천

- 사내 예시 JD와 스크랩한 공고는 현재 코드에서 SAMPLE_JDS 메모리 레지스트리에 보관됩니다.
- 채용 공고 텍스트는 ChromaDB에 넣고 이력서와의 cosine 의미 유사도를 계산합니다.
- 단건 JD 매칭은 의미 유사도 30%, LLM 심층 평가 70%를 결합해 최종 점수를 만듭니다.
- LLM 결과에는 3줄 요약, 강점, 누락 역량을 포함하도록 구조화합니다.
- 추천은 유사도가 높은 공고를 우선 선택하고, 동일 기업·직무의 JobKorea/Saramin 중복 게시를 연결할 수 있습니다.
- LLM 또는 벡터 검색을 사용할 수 없으면 규칙·키워드 기반 결과로 폴백하는 경로가 있습니다.

## 제공자 처리 메모

설정은 backend/.env의 OPENAI_API_KEY 하나를 읽습니다. 코드가 키 접두어를 보고 OpenAI와 Google 키를 구분해 이력서 추출 및 임베딩 경로를 선택합니다. 심층 평가 경로는 OpenAI ChatOpenAI를 사용하며, 사용할 수 없으면 평가 폴백을 반환합니다. 키 이름과 실제 제공자 선택이 혼동될 수 있으므로 운영 전 설정 구조를 정리할 필요가 있습니다.

## 저장 경계

ChromaDB는 CHROMA_PERSIST_DIR에 로컬 파일로 저장됩니다. 지원자 이력서나 JD용 관계형 클라우드 DB는 연결되어 있지 않고, 기본 채용 공고 목록은 프로세스 메모리에 있습니다. 서비스 재시작 시 메모리 목록과 영속 벡터 저장소의 상태가 달라질 수 있습니다.
